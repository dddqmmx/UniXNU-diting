## 3. 核心问题定位（本阶段关键突破）

虽然 `QCA6490` 硬件扫描、`CoreWiFi` 只读查询与 `PF_SYSTEM` 事件通道全部正常，但在设置 -> Wi-Fi 界面中仍不显示网络列表、切换开关也未触发驱动 `power_set`。

结合 `24B156` 原生 `/usr/sbin/wifid` 反汇编与实机 `wifi27-5` 进程线程栈分析，已明确问题位于用户态 `wifid` 内部，具体现象与根因如下：

1. **`WiFiDeviceOpen` 未完成执行**
   - `24B156` `wifid` 中 `WiFiDeviceOpen` 应依次请求 `type 106`（RSSI 边界）、`type 12`、`type 254`（`kHwSupportedChannels`）、`type 207`（`kChannelsInfo`）并建立事件监听。
   - 实机日志证实这些请求均未到达驱动；已进入驱动的查询均来自 `CoreWiFi`（仅用于设置页读取当前状态），而扫描与开关控制需经由 `WiFiManager` / `WiFiDeviceManager` 队列派发。

2. **实机 `wifid`（PID 48）全部 8 个线程状态分析发现两处明确卡死**：
   - **阻塞点 A（核心，直接卡死 `WiFiManager` 串行队列）— `th#1` 在 `SCPreferencesLock` 写锁文件时阻塞于内核 `VNOP_WRITE`**：
     - 用户态调用链：`__WiFiManagerHeartBeatFire` → `WiFiManagerFlushKnownNetworksCache` → `__WiFiManagerSetProperty` → `SCPreferencesLock(prefs, wait=TRUE)` → `write(fd=15, "48\n", 3)`。
     - 内核态调用链：`unix_syscall` → `write` → `writev_internal` → `fp_writev` → `vn_write` → `VNOP_WRITE`，长期休眠未返回。
     - 因为该任务运行在 `WiFiManager` 串行工作队列上，一旦永久阻塞，所有后续设备打开、扫描与电源开关请求全部被挡在队列之外。
   - **阻塞点 B（日志/追踪与安全链路死锁）— `th#3` 阻塞于满队列的 Mach 端口并持锁卡住 `th#4`/`th#5`/`th#6`**：
     - `th#3` 调用链：`CoreWiFi` → `Security` → `Foundation`/`CoreFoundation` → `Security` → `libsystem_trace` → `libdispatch` → 同步 `mach_msg`（消息 ID `11601` / `0x2d51`），在内核中阻塞于 `_ipc_mqueue_full`（目标端口队列 `5/5` 已满，无人消费）。
     - `th#3` 阻塞期间持有 `libsystem_trace`/`libdispatch` 内部用户态锁，导致 `th#4`（`WiFiPolicy`）、`th#5`（`wifid` → `Security`）、`th#6`（`WiFiPolicy`）三个线程全部在 `libsystem_trace` 内等待同一把锁（`__ulock_wait`）。

3. **已确认的次级驱动待修正项**：
   - `drivers/DitingWifi/DitingWifiNet.cpp` 中 `kSupportedChannels` / `kHwSupportedChannels` 当前把 QCA6490 上报的 102 个频点（含 `>= 5955 MHz` 的 6 GHz 频点）全部按 5 GHz 公式 `(mhz - 5000) / 5` 编码，需过滤为标准 2.4 GHz（`2412..2484 MHz`）与 5 GHz（`5180..5885 MHz`）信道。
   - 对比 `IO80211` 与 iPadOS 27（`24A446`）参考实现 `sheng/package/WifiNet.cpp`：`IO80211` 在 `IOServiceOpen` 返回 `kIOReturnUnsupported` 时会无缝回退到 BSD socket `ioctl`（`SIOCGA80211`/`SIOCSA80211`）；待上述阻塞解除后，如 `Diting80211UserClient` 仍有兼容差异，也可对照评估该路径。
