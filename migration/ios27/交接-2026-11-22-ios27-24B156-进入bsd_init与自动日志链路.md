# Diting iOS 27.2.1（24B156）适配交接文档（2026-11-22）

## 1. 当前总体状态

- **目标**：为 Redmi K50 Ultra（`diting`，SM8475，8 核，4 KiB 页）适配 iOS 27.2.1（`24B156`，`iPhone18,2`/`V54AP`，`arm64e` `MH_FILESET`）直至完整启动 `bsd_init()`、存储/USB 与用户态。
- **分区与设备边界**：
  - **未写入任何设备分区**，持久 `boot_b`（`services198`）、`Data` 与 `userdata` 均未改动；所有实机试验均为临时 `fastboot boot` 且使用 `--skip-image-verification`。
  - 设备 `1d4eb066` 当前停留在 **Fastboot** 模式（`product: diting`，`unlocked: yes`），无遗留构建/采集后台进程。
  - 本次仅整理交接文档，未执行 `git commit`/`push`。
- **最新实机里程碑（`boot-diag-25b` / `boot-diag-25d`）**：
  - 内核已从 `DarwinBoot.efi` -> `start_first_cpu` -> `arm_vm_init` -> `arm_init` -> `machine_startup` 完整穿过 **`corecrypto`**、**`IONVRAM`**（CHRP）、**`AppleImage4`**、**`AMFI`**（`iPhone18,2` + `Enabling developer mode`）、**`Sandbox`（Seatbelt）**、**`vnguard`**、**`IOKit`/`IOService::_Dispatch`**，**正式进入 `bsd_init()`**（打印 `Copyright (c) 1982..1993`、`MAC Framework successfully initialized`、`16384 buffer headers and 10240 cluster IO buffer headers`、`IOCPUInterruptController: not registry member at registerService()`）。
  - **免手动抄屏的自动化日志回读链路已打通**：内核崩溃或命中 `diting_early_deadline=<秒>` 时自动经 PMK8350 SPMI + IMEM + PSCI 软复位回 Fastboot，由宿主脚本自动引导 `recovery-log-reader.img` 通过 tracefs kprobe 读取 12 份相位偏移 `D27L` DRAM 日志并自动重启回 Fastboot（`boot-diag-25d` 完整回收 6,008 字节清晰控制台日志，`magic=0x4c373244`）。
  - **已隔离出当前核心阻塞点（8 核副核启动 vs 单核推进）**：
    - `cpus=8 smp=1` 下：`boot-diag-25b`（`diting_early_deadline=1`）在 `+27.8s` 正常命中软截止并返回（`pc=0xfffffff00ade5ad4`，`_machine_idle+0xfc`）；但 `diting_early_deadline=5`（`boot-diag-25c`）、`15`（`boot-diag-25`）及无截止（`boot-diag-24`/`24b`）均在 `t=1s..5s`（`IOCPUInterruptController` 之后）卡死且不再响应 IRQ/FIQ，直至 `+56.9s` 触发硬件看门狗硬复位（DRAM 掉电清零）。
    - `cpus=1 smp=0` 下：`boot-diag-25d`（`diting_early_deadline=10`）**未卡死**，完整运行满 10 秒并在 `_processor_idle+0xe8`（`pc=0xfffffff00abf934c`）干净软复位回 Fastboot，回收完整 6,008 字节日志。

## 2. 相对 2026-11-20 交接的新增修复与改动

### 2.1 `arm64e` ABI / PAC 与 SM8475 EL1 兼容修复
1. **SM8475 QHEE EL2 拦截 `CNTP_CTL_EL0`**：
   - 新增 `patches/xnu-ios27/sm8475-no-cntp-ctl.patch`（`series` 位于 `sm8475-secondary-affinity.patch` 之后），在非 `XNU_FILESET_REFERENCE` 构建中跳过 `osfmk/arm64/machine_routines.c` 对 `CNTP_CTL_EL0` 的 EL1 写操作，解决 `undefined kernel instruction`（`pc=0xfffffff00ade5584`）。
2. **`-fptrauth-function-pointer-type-discrimination` 对齐 24B156**：
   - 新增 `patches/tooling/linux-arm64e-fp-type-discrimination.patch`（并在 `scripts/build-diting-ios27.py` `select_compile_environment()` 中加入 `fp_type_discrimination` 哈希项）：`arm64e` 构建统一启用 `-fptrauth-function-pointer-type-discrimination`，修复 `kmod_start_func_t`（`0xe4fe`）等跨内核/kext 函数指针 IA PAC 失败。
3. **DriverKit `iig` `SimpleMemberFunctionCast` 成员函数指针 PAC 失配**：
   - 根因：Linux `clang-24` 支持 `-fptrauth-function-pointer-type-discrimination` 与成员指针重签（`_ptmf2ptf`：`0xa83d -> 0x4a27`），但不提供 Apple 私有内建 `__builtin_load_member_function_pointer`，导致 `iig` 生成的 `.iig.cpp` 退化为 `union` 强转，传入 `IOService::_Dispatch` 的 handler 仍带成员指针 diversity 而触发 IA PAC trap（`pc=0xfffffff00b312f54`）。
   - 修复：新增 `patches/xnu-ios27/iig-ptrauth-member-cast.patch`（位于 `series` 中 `diting-early-fb-trace.patch` 之前），修改 `iokit/DriverKit/Makefile` 与 `iokit/Tests/TestServices/Makefile`，在 `#ifdef KERNEL` 下将后备宏改为 `((cfnty) OSMetaClassBase::_ptmf2ptf(&(self), (void (OSMetaClassBase::*)(void))(func)))`。已通过 `llvm-objdump` 确认 `__ZN9IOService9_DispatchEPS_5IORPC` 全部改走 `_ptmf2ptf` + `autia` + `pacia`，实机穿过 `IOService::_Dispatch`。
4. **NVRAM CHRP 镜像与重复 `pthread` kext**：
   - `scripts/build-diting-ios27-bootimg.py` 新增 `empty_nvram_proxy()`，构造合法 CHRP 头（`nvram`/`common`/`free`、Adler-32、`nvram-bank-size`/`count`/`current-bank`），解决 `IONVRAMCHRPHandler creation failed @IONVRAM.cpp:1602`。
   - `os-profiles/ios-27.2.1-24B156/profile.toml` 与 `board.toml` 从 iOS 27 `roots` 移除 `com.apple.kec.pthread`（`CONFIG_XNU_SOURCE_PTHREAD=y` 已将 `libpthread` 编入内核，避免 `Re-initialisation of pthread kext callbacks @pthread_shims.c:637`）。
5. **驱动弱符号导出与增量重编修复**：
   - `scripts/build-diting-ios27-drivers.py` 的 `provider_exports()` 忽略 `'weak' in fields`，避免二次构建时跳过 `OptionalProviders.S` 存根导致链接缺符号。
6. **ARMv8.5 MTE 核查结论**：
   - 扫描保留的 24B156 kext `__TEXT_EXEC` 共 `10,145,792` 条指令：**0 条 `MSR TCO`、0 条 MTE tag 指令**（`com.apple.kernel` 由本地无 MTE 源码内核替换，`MSR TCO` 仅存在于 Apple 原始内核中）。SM8475 不支持 MTE 不构成 24B156 kext 运行阻塞。

### 2.2 自动化日志抓取与软截止机制
- `patches/xnu-ios27/diting-ramoops-console.patch`：
  - 在 `0xa7300000` 写入 12 份相位偏移 `D27L` 日志副本（`STRIDE = 0x8000`、`CAPACITY = 0x7800`、每份偏移 `(c & 3) * 0x100`，避开实机 LPDDR5 在软复位期间每 `0x400` 的 `0x100..0x1ff` 全 `0xff` 衰减带，并抵抗其余区域的 `1->0` 衰减）。
- `patches/xnu-ios27/diting-early-fb-trace.patch`：
  - 修正 `iso_font` 位序（`1u << gx`）；增加 `virtual_space_start != 0` 保护、启动步进标签 `S1:printf`..`S11:mstart`、`diting_early_fb_panic` 无条件输出与控制台尾部显示；
  - 新增 `diting_early_panic_fastboot_init()` / `diting_early_panic_fastboot_reset()`（`diting_panic_fastboot=1` 时写 PMK8350 `SID0 SDAM7100@0x48` + IMEM `0x146aa65c=0x77665500` + PSCI `0x84000009` 软复位回 Fastboot）；
  - 新增 `diting_early_deadline=<秒>`，在 `osfmk/arm64/sleh.c` 的 `sleh_irq()` 与 `sleh_fiq()` 入口检查 `cntvct_el0`，超时即打印中断现场 `pc`/`lr`/`cntvct` 并软复位回 Fastboot（抢在 ~50s 硬件看门狗擦除 DRAM 之前保存现场）。
- 宿主自动化脚本：`diting-work/tmp/services227/run-and-read-ios27.py`（检查 `1d4eb066`/`diting`/`unlocked` -> `fastboot boot` -> 等待自动回 Fastboot -> 引导 `services171/recovery-log-reader.img` -> 自动识别 ADB 5038/5037 端口 -> tracefs kprobe 读取 12 份 `D27L` -> 每字节过滤落入 `0x100..0x1ff mod 0x400` 的 3 份后对剩余 9 份做 `>=2/9` 位恢复 -> 保存 `d27l.log` -> `adb reboot bootloader`）。

## 4. 下一步接续建议（按优先级）

1. **在 `cpus=1 smp=0` 下延长截止时间，查明 `bsd_init()` 后续推进状态（无需重编内核）**：
   - 使用现有 `kernel.diag-25.macho`，仅通过 `build-diting-ios27-bootimg.py` 打包 `cpus=1 smp=0 diting_early_deadline=30`（或配合 `bsd_init()` 内补充 `diting_ramoops_diagnostic_write` 阶段日志），确认 `cpus=1` 下是否卡在 `IOKit` 设备匹配 / `vfsinit()` / `native_source_storage_start()` / `diting_usb_start()` / `vfs_mountroot()`，以及 `DitingUfs` 与 `DitingUsb`（`ffff:0128 /dev/ttyACM0`）是否启动。
   - 注意：`drivers/DitingUsb/DitingUsbDevice.h` 在 `diting_battery_usb_online() == -2` 时会直接退出 worker；若要在 iOS 27 早期直接拉起 CDC-ACM USB 控制台，需接通 `DitingBattery` 或为诊断模式放开该检查。
2. **定位 `cpus=8 smp=1` 下 `t=1s..5s`（`IOCPUInterruptController` 之后）触发硬件看门狗的根因**：
   - 重点排查 `ArmCpu` / `sm8475-secondary-affinity.patch` 在 24B156 `arm64e` 上的副核复位路径（对照 iPadOS 18 `services174–180` 经验：副核页表 PoC 刷新、早期 VBAR 切换时机、PAC key 初始化、`-mno-implicit-float` 隐式 NEON、`ArmCpu` 启动超时/PSCI `CPU_ON` 与 GICv3 redistributor 唤醒）。
   - 可先测试 `cpus=2 smp=1` + `diting_early_deadline=3` 并在 `ArmCpu` 启动副核前后向 `diting_ramoops_diagnostic_write` 打点，快速区分是 CPU1 进入复位向量前还是进入 `arm_init_cpu` 后锁死。
3. **推进 `XnuPrelink` 严格预链接（341 -> 0 存根 + 1 数据引用）**：
   - 优先补齐启动关键链路的剩余存根：`IOStorageFamily`（9）、`AppleMobileFileIntegrity`（剩余 ~9）、`sandbox`（剩余 ~15）、`apfs`（118）、`AppleImage4`（1）、`AppleARMWatchdogTimer` 数据引用（1）。
   - 保持 `board.toml` 与 `profile.toml` 不引入 `--allow-missing`，确保 `tests/test_diting_ios27.py` 与 `XnuPrelink` 单测持续全绿。
4. **打通 UFS 挂载、OS/SystemOS 布局与用户态带起**：
   - 在不覆盖 `boot_b`（`services198`）与现有 `Data` 的前提下验证 `24B156` 存储窗口读取、trustcache 加载及 `launchd` 启动。
