## 已完成的重要修正

### services206–207：GMEM 事件传输

206 在强制 GMEM 的三个 Vulkan 线性 BGRA 用例中复现红蓝交换，sysmem 对照无像素错误。旧适配在 `event_blit_run` 中强制 `RB_RESOLVE_SYSTEM_BUFFER_INFO.COLOR_SWAP=WZYX`，覆盖线性 BGRA 所需的 WXYZ。207 对照固定 Mesa 源恢复格式自身的交换契约，并增加独立事件 load/store 计数与首帧 CPU 像素检查。

207 完整构建、启动后，一次矩阵 auto43/43、sysmem39/39、gmem39/39 全部通过；64,704 条 trace 的 missing/skipped/kernel drops/recovery 全为 0。208/209 均保留该 GPU 包。但用户在207和208仍看到颜色错误与闪烁，这个局部修复没有闭合正常显示问题。

### services208：刷新通知

保留原本的 HIGH thread-call 优先级，增加 `THREAD_CALL_OPTIONS_ONCE`，在 XNU 内使用 `THREAD_CALL_DELAY_SYS_CRITICAL` 关闭通知 timer coalescing。保持周期相位，迟到时选择最新已到期周期，不发送旧的或未来时间戳。事件25新增 due/fired/period/skipped/armed，解码器校验时钟证据。

驱动 SDK 不导出内部 urgency/API，因此纯色控制器使用公开的普通 delayed thread-call；明确 critical urgency 仅用于 XNU 内部刷新通知。编译中的 IOReturn 窄化也已用显式 `uint32_t` 转换修正。

### services208：有界纯色输出隔离

`display solid blue|green|red MS` 默认关闭，MS 为 1000–60000。控制器保存两个 VIG 的 FORMAT/UNPACK/CONSTANT_COLOR 六个原值，flush 两个 VIG；只有恢复 flush 退休且帧计数前进才报告 restored=1。电源关闭时不访问 DPU，重试有界，配置所有权变化时不覆盖新配置。

1秒蓝色恢复检查和60秒观察均恢复成功，writes14/error0/restored1。用户明确回答 **“稳定的纯蓝色”**。该对照使用 FORMAT `004237ff`、UNPACK `03010002`、蓝色 CONSTANT_COLOR `ffff0000`。

**此结果只证明在固定色源及该取色配置下，后段可以正确、稳定地输出蓝色。** 它绕过 GPU/DDR framebuffer fetch，同时改变了 UNPACK；不能据此排除正常 framebuffer 格式、缓存一致性或扫描同步问题，更不能把正常 UI 颜色记为 PASS。

## 内存与带宽：仍是待验证方向

用户指出真实 UI 的多 pass、模糊、纹理读取和中间 buffer 写回，比离屏负载更可能受 DDR/LLCC 或渲染策略影响。这一方向尚未完成实测，也未被排除。

208 读到 GPU 请求900 MHz、requested_DDR=11；MC3/SH5 BCM 请求 DDR3,196,000 kHz、LLCC1,066,000 kHz，memory stage4/error0、cache_ready1。后续已增加 BCM 请求和 LLCC 配置，不能继续把“只有 GPU 在投 DDR”当作当前完整状态。**请求和寄存器回读仍不是实际频率或持续带宽证明**；GMU PERF/BW 仍为0，实际 DDR 频率 UNQUALIFIED，持续物理带宽 UNMEASURED。

历史205在1ms量化 LLCC 窗口中看到约19.071/42.795/38.011 GB/s峰值，各次已恢复。这些短窗口计数不是持续 DDR 容量。DDR BWMON 因 enable0、filter_mask2 等所有权条件被拒绝借用（mask802/writes0）；不能把零值解释成零带宽，也不要强借计数器。208 内存页快照为 free126483、available782498，单次快照不足以判断负载峰值内存压力。

运行时仍有 `nocb` 证据；不能仅凭这个字符串认定所有 UI 都走 sysmem。207 GMEM 矩阵通过也不能证明真实 UI 所有 pass 的格式、导入、生命周期和外部内存访问都正确。
